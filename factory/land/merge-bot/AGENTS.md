# The Merge bot

The Merge bot (`factory/land/merge-bot/`, started by `factory/bin/merge-bot.ts`) runs from `.github/workflows/merge-bot.yml`, checked out from the default branch, with the agents' GitHub App token: one Merge bot run per PR event, and a Sweep of every open PR on a push to `dev`, when CI completes on that push (the Sweep that reads `dev`'s red), and on a cron.
It keeps a state record in one PR comment, calls the Judges, posts the Review check (`agent-review`) and the Land gate (`land-gate`), and enables the merge.

The same comment holds, above the record's own line, the ledger of the review's findings, for the reader of the PR: per round, and for the Delta read, what it posted and where each finding stands now.
A finding the Author rejected links the reason; one whose latest answer is the Owner's, by hand, is answered by the Owner and links the answer, whatever its severity and whoever closed it, since a round that read the Owner's answer and left the finding out fixed nothing; an Important the read after its last report no longer reports, a later round or, past round 3, a Delta read once the record names one, its thread closed by the App, is fixed, confirmed; one the Owner's Land approval closed, the App's reply in its thread saying so, is landed open; one closed by hand is closed with no round confirming it; a Nit the Author says it fixed, by the Stop hook's record, a line of its own in the comment of the Author's machine account, is fixed by the Author's word, since no later round reads a Nit again, with GitHub's outdated mark beside it; a Nit closed otherwise has no answer; the rest is open.
Each decision rewrites the ledger when what it shows changed, and a decision that resolves threads reads them again and writes the ledger with its final record, since no later decision may come before the PR lands, so it is true whenever it is read.
The record keeps its marker and its keys, on a line of its own, which no line of the ledger is.

The Owner's Land approval lands a PR held for the Owner whatever Important threads are open; each such Important lands open, and leaves a trace, once the PR lands: while `dev` is red, the PR waits and its threads stay open.
A Land approval covers only the findings the Owner could read when giving it: it counts only when the Owner's `labeled` event comes after the head was pushed and after the App's latest review of a round or a Delta read was posted, the one whose body carries its marker, a later second than the review's (a reply the App posts in a thread, which GitHub lists as a review too, is no new read), since a review posted after it, a round or a Delta read, may post an Important the approval would land open unread.
One that no longer counts goes, with a comment that says why and that the Land gate says whether the PR still waits for the Owner, posted before the label goes, so a run that stops between them posts it again rather than never.
The Merge bot first opens one follow-up issue for the PR, as the App, whose token holds `issues: write`: its title names the PR, and it lists each Important still open by its file and what it says, linked to its thread, and asks to fix it or to say why it stands.
A finding is the Code review's text about the PR and the issue may become an Author's task, so each is quoted in a code span, as data, and cites no line, which later changes move.
The issue's number goes to the state record (`followUpIssue`) as soon as it is opened, before any thread closes, so a run that reads the PR again, or retries the landing, opens no second one; none is opened when no Important is open.
Then the App replies in each open Important thread that the Owner's Land approval lands it open, linking the issue, once per thread, and resolves it.

`decide.ts` assembles the rules, each in the file its opening comment names: the state record, the review the record asked, the read a patch needs, what the gate and the labels say.
`main.live.ts` is the shell: it reads a snapshot, asks `decide.ts`, performs the steps and writes the ledger (`ledger.ts`); what it reads of GitHub's answers is in `readings.ts`, its calls to GitHub in `github.ts`, and the Env it builds from the job's variables, the logins it trusts among them, in `env.ts`.
