# The Judges and the Code review

The Judges answer through a JSON schema: the Done judge, a fork of the Author's session, and the Routing judge and the Code review, headless Agent SDK calls. Every Judge and every Stop hook fork reads with `Read`, `Grep`, `Glob` and one read-only `git` command per `Bash` call, under the guard of `review/tool-guard.ts`: no write tool, never an empty tool list, never `Monitor` for a fork. Each text a Judge reads lives in a `*-prompt.ts` file under `scripts/land-loop/`.

The Code review is Claude Code's native `/code-review`, run in its own job (`.github/workflows/code-review.yml`, `review/run-review.ts`) with read-only tools under a guard (`review/tool-guard.ts`). The Merge bot dispatches it, reads its result from the run's artifact, and posts the Important and Nit findings inline (`review/post-plan.ts`), in at most three Review rounds; a PR that touches an `ownerPaths`, `factoryPaths` or `deepReviewPaths` path or the factory config gets a security pass in the same round (`review/security-prompt.ts`), posted as `(security)` findings. Each round's review opens with what it posted in plain words, the security pass's share apart, such as `Round 3: 2 Important (1 security), 5 Nit (2 security). 2 pre-existing defects not posted.`; the Delta read's opens with `Delta read: `. A round that posts an Important sends the PR back to draft; so does a round that posts a Nit and no Important, on a PR the Author's machine account opened: the Review check stays green, the Land gate reads `Draft: the author's turn.`, and nothing merges the PR until its Author stops again. A round always follows a round that posted an Important, on the Author's next push, up to round 3, whatever the Routing answer says of the delta; after a round with no Important, a push is read again when it needs a read. A push that only answers the Nits of the last round, which posted no Important, needs none (`withNitAnswers`): its delta starts at the head that round read, touches only files the round posted a Nit on, outside `deepReviewPaths`, in at most 100 lines. Each round after the first reads the earlier findings with the answers of the Author's machine account and of the Owner, no other login's, and reports again every earlier Important that is still wrong: the Merge bot posts each as a reply in its open thread, and resolves the open Important threads of earlier rounds the round leaves out. The fix of an Important is never declared by its author; a Nit's is, in the Merge bot's ledger alone, since no later round reads a Nit again. An Important in round 3, or a push after it that needs a read other than the Delta read below, holds the PR for the Owner, the last reader: the Owner's Land approval for the current patch then lands it whatever Important threads are open. No Important closes without a trace: each ends fixed, confirmed by a read; rejected, with the Author's reason; or landed open by the Owner's Land approval, which the Merge bot says in its thread when it resolves it, and which one follow-up issue asks to fix or to answer (`merge-bot.md`).

After round 3, a push gets a Delta read, a light Code review of its delta from the head round 3 read, with the PR's security pass, whatever the PR's Review depth, in two cases. A push on a PR with an open Important, round 3's or an earlier Delta read's, gets one before the Owner is asked: round 3 has no next round, and without it the Owner approves with no word on which Importants the Author's fix answered, and nobody knows afterwards what landed. Shown the open Importants alone, with their answers, it reports again each one still wrong, which the Merge bot posts as a reply in its thread, and the Merge bot closes the others as fixed, as it does after a round; the PR stays held for the Owner, who then reads threads closed because a read confirmed the fix and threads open because it did not. And a push after a round 3 that posted no Important, which answers its Nits in the Nit files and touches at least one test file beside a Nit file (`x.test.ts` for `x.ts`), within the bounds above, on a PR that lands `auto`, needs a read but holds nothing: an unread test could switch a guard's test off, and calling the Owner for a Nit's answer costs more than one light read. The Delta read is a read of its own kind, not a round 4: the review job numbers it 4, but the state record keeps it apart, in `deltaReadPatch`, and leaves the three rounds as they are, so each later push gets its own, its delta still measured from round 3's head: one read per push, so it converges. It posts its Importants alone: a Nit is not worth another turn. No Important lands the PR by its route; an Important it finds holds the PR for the Owner, as round 3's does, and a PR held already keeps its hold.

The Code review loads no project file by itself, so that a pull request never changes its reviewer's guide: `review/run-review.ts` puts `REVIEW.md`, `AGENTS.md` and every rule under `.claude/rules/` in its prompt, read from the checkout of `dev`. Each is a regular file of that checkout: a link, the file's own or a directory's on the way to it, fails the job (`lib/guide.ts`), since its target would reach the prompt next to the job's token.
